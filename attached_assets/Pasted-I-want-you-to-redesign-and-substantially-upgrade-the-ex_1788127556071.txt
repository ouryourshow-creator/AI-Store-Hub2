CLERK

Continue using Clerk authentication.

Do not create a second authentication system.

Secure all admin routes.

Do not rely only on client-side UI hiding for administrator security.

PERFORMANCE

Dashboard analytics should not result in hundreds of database queries.

Avoid N+1 queries.

Aggregate data efficiently.

Use server-side aggregation where appropriate.

Use parallel queries where safe.

Cache expensive dashboard analytics if needed, while ensuring data does not become misleadingly stale.

Pagination must be server-side for large tables.

Do not fetch thousands of orders or customers into the browser just to filter them.

Search and filtering should be server-side when datasets can become large.

MONEY HANDLING

Never use floating-point arithmetic for financial calculations.

Follow the existing application's monetary storage conventions.

Prefer integer minor units or PostgreSQL numeric/decimal where appropriate.

Ensure:

Revenue calculations

Discount calculations

Cashback calculations

Referral rewards

Order totals

are mathematically reliable.

TIME AND DATE HANDLING

Use consistent timestamps.

Respect the existing application's timezone handling.

Dashboard date filters must not accidentally move orders between dates because of UTC/local-time conversion problems.

Keytopia primarily operates in Egypt, but do not make unsafe assumptions if the application already has timezone configuration.

DATA INTEGRITY

This is critical.

Changing an order status must not accidentally:

Issue cashback twice

Issue referral rewards twice

Count a coupon twice

Create duplicate transactions

Delete valid customer history

Corrupt order totals

Use transactions when multiple database operations must succeed together.

Implement idempotency where business events can be triggered more than once.
